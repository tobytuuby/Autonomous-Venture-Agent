## 2. Current behavior

### 2.1 Slow drift

SyntheticAnomalyAnalyzer._detect_drift groups records by venture and service class, compares requested-unit maximum and minimum values, and emits:

- code: SLOW_DRIFT;
- status: REVIEW_REQUIRED;
- finding hash;
- source record IDs and hashes;
- effect: none;
- capability_granted: false.

This is review evidence only. It does not classify drift as ZERO, TOLERATED, or BLOCKING.

### 2.2 Input-integrity failures

The analyzer rejects several malformed or unsafe inputs with AnomalyDenied, including:

- live authority;
- effectful input;
- configuration mismatch;
- record-hash mismatch;
- missing provenance;
- canonical-hash mismatch.

These denials are useful negative controls, but they are not blocking-drift events. They do not create a drift case ID, preserve a before/after state envelope, or invoke a freeze.

### 2.3 Existing freeze and evidence primitives

SyntheticOperationsKernel already provides relevant synthetic primitives:

- freeze_venture;
- freeze_service;
- quarantine;
- grant-revocation record creation;
- evidence_hash;
- canonical_hash;
- record_hash;
- replay validation;
- configuration-fingerprint validation;
- append-only SQLite journal behavior.

The missing behavior is the controller that converts a qualifying blocking drift into a freeze event and a separately preserved evidence event.

## 3. Required hardening

### 3.1 Drift classification

Add an explicit classification contract:

| Classification | Meaning | Required action |
|---|---|---|
| ZERO | Observed state equals expected authoritative state | Record case result; no freeze |
| TOLERATED | Pre-declared, bounded, non-authority-affecting difference | Record reason, bound, approval, and expiration; no automatic freeze |
| BLOCKING | Unexplained authority, ledger, provenance, credential, customer-state, policy, or configuration difference | Freeze immediately; preserve evidence; prohibit release |

The classifier must be deterministic and must include:

- drift_type;
- affected_scope;
- expected hash/value;
- observed hash/value;
- tolerance rule, if applicable;
- classification;
- reason;
- source IDs and hashes;
- policy/configuration fingerprint;
- case ID.

A drift must never become TOLERATED merely because a summary or model output says it is acceptable.

### 3.2 Blocking-freeze transition

Add a P7-owned controller or service boundary rather than coupling the stateless analyzer directly to SQLite internals.

Recommended flow:

1. Validate the drift event and its provenance.
2. Classify it.
3. If ZERO, persist a case result only.
4. If TOLERATED, persist the bounded exception and reviewer/expiry metadata.
5. If BLOCKING:
   - create a freeze request for the smallest affected scope;
   - submit it through SyntheticOperationsKernel.freeze_venture or freeze_service;
   - verify the returned status is FROZEN;
   - record the freeze action ID and record hash in the evidence envelope;
   - prevent recovery or release until review.
6. If freeze fails, fail closed and emit a higher-severity freeze-failure result.

The controller must not grant, restore, or widen authority. It must operate entirely within the existing synthetic/effect-free boundary.

### 3.3 Evidence preservation

Create a separate immutable drift-evidence record. It must not rely only on the anomaly finding hash or operation record hash.

Minimum fields:

- case_id;
- drift_event_id;
- drift_type;
- classification;
- affected portfolio/venture/service scope;
- detected_at;
- preserved_at;
- preservation_latency_seconds;
- source_commit;
- source_file_hashes;
- configuration_fingerprint;
- environment_identity;
- command;
- expected_state_hash;
- observed_state_hash;
- before_snapshot_sha256;
- after_snapshot_sha256;
- raw_output_path;
- raw_output_sha256;
- freeze_action_id;
- freeze_record_hash;
- reviewer_classification;
- status;
- limitation or simulation reason.

The preservation check must assert:

preserved_at - detected_at <= 900 seconds

For deterministic tests, timestamps may be supplied as fixtures. The report must clearly label this as timestamp-contract validation rather than a real 15-minute wall-clock observation.

### 3.4 Evidence-envelope integration

The existing P7 execution structure is compatible with parameterized tests. The required denominator is individual case records, not individual test methods.

The harness should emit:

- p7-execution-manifest.json;
- p7-case-results.jsonl;
- p7-evidence/ raw files and hashes;
- p7-authority-matrix.md;
- p7-recovery-matrix.md.

Each parameterized case must produce one immutable JSONL result with its own case ID, expected result, observed result, hashes, timestamps, and reviewer classification. A single test method producing 81 records is acceptable; one aggregate assertion without 81 retrievable records is not.

## 4. Exact test-harness changes

The current P6.3 unittest pattern asserts findings in memory and does not emit P7 evidence envelopes. Add a P7-specific harness with these components:

### 4.1 Case definitions

Create a machine-readable case registry containing:

- 81 authority cases: 9 authority fields × 9 state families;
- 12 recovery cases: freeze, revoke, quarantine, restore, rollback, and wind-down × normal/injected failure;
- expected classification and expected containment action;
- synthetic fixture identifiers;
- policy/configuration fingerprint.

### 4.2 Case runner

For every case:

1. load the fixture;
2. compute the before-state hash;
3. inject the specified synthetic drift or failure;
4. invoke the classifier/controller;
5. compute the after-state hash;
6. verify the expected result;
7. verify freeze status for BLOCKING cases;
8. write the individual evidence envelope;
9. hash the raw output;
10. append one JSONL case result;
11. update the manifest.

### 4.3 Independent verification pass

The reviewer pass must independently recompute or verify:

- source hashes;
- configuration fingerprint;
- before/after state hashes;
- finding hash;
- freeze record hash;
- evidence hash;
- preservation latency;
- denominator uniqueness and completeness.

The implementer cannot generate the sole acceptance decision.
